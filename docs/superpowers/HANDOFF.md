## 3. 다음 세션이 가장 먼저 할 일

### 3-A. Task 13 수정분 재리뷰 (커밋 `c104ff9`)

주간 상세 페이지의 dangling count 버그를 고친 커밋이다. 리뷰어가 지적한 내용:

> `이번 주 전체 ({items.length})` 제목 아래에 `items.filter(!pick)`를 렌더링하는데,
> 가드가 `items.length > 0`를 본다. 그 주 항목이 **전부** 하이라이트로 뽑히면
> 제목은 "이번 주 전체 (3)"인데 그리드가 비어 있다. 초기 몇 주의 정상 시나리오다.

수정은 남은 목록을 한 번 계산해 개수·가드·map이 같은 집합을 쓰게 하고, picks가 있으면 제목을
"이번 주 나머지"로 바꾼다. **타입체크·빌드·테스트는 통과했지만 리뷰어 검증을 받지 못했다.**

리뷰어에게 함께 확인시킬 것 (원 리뷰의 ⚠️ 항목):
- 빈 상태(`content/` 없음)에서 `/people`, `/weekly`, `/`의 **실제 HTML을 curl로 받아** 한국어
  빈 상태 문장이 나오는지. 이전 구현자는 이걸 "코드를 읽어서 확인"으로 대체했다.
- 다른 라우트에도 같은 패턴(한 집합으로 개수를 세고 다른 집합을 렌더링)이 있는지.

### 3-B. Task 14 리뷰 (커밋 `640ddf3`)

워크플로 2개 + 알림 스크립트 + README. 리뷰가 시작됐다가 세션 종료로 중단됐다. 다시 띄울 것.

리뷰에서 반드시 다룰 것:
- **`shellcheck`가 이 머신에 없다.** `bash -n`은 문법만 본다. 손으로 읽어야 한다 —
  공백/글로브 문자가 든 소스 키에서 깨질 따옴표 없는 확장, `set -euo pipefail`과 정상적으로
  0이 아닌 값을 반환하는 명령의 충돌, 알림 0건일 때 루프 동작, 백틱·`$`가 든 에러 메시지에서
  깨질 heredoc.
- 구현자가 플랜을 의도적으로 벗어난 부분: 중복 이슈 방지를 `gh issue list --search`(부분 문자열
  검색)에서 **`source-down` 라벨이 붙은 열린 이슈 제목을 받아 로컬 정확 비교**로 교체했다.
  더 신뢰할 만한지, 새 실패 모드(페이지네이션 한도, 라벨 부재, 빈 결과와 오류 구분)를 만들지
  않았는지 판단할 것.

## 4. 아직 하지 않은 바깥 작업 (사용자가 이미 승인함)

사용자는 **public 레포 생성**과 **API 키 제공**에 동의했다. 키는 이미 `.env.local`에 있다
(`.gitignore`의 `.env*`로 제외됨, 108자, 형식 확인 완료). `gh`는 `YongHakLee` 계정으로
`repo`·`workflow` 스코프 인증되어 있다.

순서대로:

1. `gh repo create AI-Tech-Followup --public --source=. --remote=origin --push`
2. `gh secret set ANTHROPIC_API_KEY < (키 값)` — `.env.local`에서 읽을 것
3. `gh label create source-down --description "수집 소스가 연속 실패" --color D93F0B`
   — 이 라벨이 없으면 알림 스크립트의 `gh issue create`가 실패한다
4. **미뤄둔 라이브 검증 일괄 실행** (아래 5절)
5. Vercel 연결 및 배포 — `npx vercel login`은 브라우저 인증이라 사용자가 직접 해야 한다.
   세션 종료 시점에 완료 여부 미확인. `npx vercel link` → `npx vercel --prod`,
   그리고 `SITE_URL` 환경변수 등록.
6. 전체 브랜치 최종 리뷰 (6절의 Minor 목록을 함께 넘길 것)

## 5. 라이브 검증 — 아직 한 번도 실행되지 않음

세션 내내 API 키가 없어 **LLM 경로가 전부 스텁과 dry-run으로만 검증되었다.** 키가 생겼으니
반드시 실행할 것:

- `pipeline/summarize.ts` 실제 호출 — 한국어 3문장과 허용 목록 안의 태그가 나오는지
- `npm run collect` (dry-run 아님) — 요약이 붙은 아이템이 `content/`에 쓰이는지
- `npm run weekly` — LLM 큐레이터가 `origin: 'llm'`으로 하이라이트를 만드는지

SDK 호출 형태 자체는 설치된 `@anthropic-ai/sdk` 소스를 읽어 검증했다 — `messages.parse`,
`zodOutputFormat`, `parsed_output` 모두 실재하고, 루트 `zod`와 SDK의 `zod/v4`가 **같은 모듈로
해석된다**(semver 호환이 아니라 동일 구현). 실패한다면 SDK 형태가 아니라 다른 원인이다.

## 6. 미결 위험

### 6-A. arXiv 저자 쿼리 형식 — 미해결

`arxivQueryUrl`이 `au:"Karpathy_A"`를 만든다. 리뷰어 주장: 밑줄 형식은 arXiv에서 따옴표 **없이**
쓰는 규약이고, 따옴표는 공백 있는 실명 구문 검색용이다. 둘을 섞으면 인덱스의 실제 저자명과
매칭되지 않아 **결과가 영원히 0건이면서 에러도 안 난다.**

세 번 실증을 시도했으나 arXiv가 이 호스트에 계속 429를 반환했다(에이전트 시도 직후, 별개
프로세스에서도 재현). **구현자의 "쿼리는 정상"도, 리뷰어의 "쿼리가 깨졌다"도 증명되지 않았다.**

- 추측으로 `pipeline/adapters/arxiv.ts`를 고치지 말 것
- GitHub Actions 첫 실행은 다른 IP라 여기서 갈릴 가능성이 높다
- 5회 연속 실패 시 이슈 자동 생성이 이걸 표면화한다
- 부수 관찰: `http://export.arxiv.org`는 이제 https로 301 리다이렉트한다. Node fetch가 따라가서
  동작은 하지만 URL이 낡았다

### 6-B. 최종 리뷰로 넘긴 Minor 목록

최종 전체 리뷰 에이전트에게 이 목록을 넘겨 어느 것을 병합 전에 고칠지 분류하게 할 것.

**고칠 값이 높은 것**
- `pipeline/highlights.ts`: **빈/공백 인트로 폴백 트리거에 테스트가 없다.** 가드에서 `&& intro`를
  지워도 12개 테스트가 전부 통과한다. 폴백이 이 모듈의 존재 이유인데 세 트리거 중 하나가 무방비다.
- `@/*` 별칭을 import하는 영구 테스트가 없어 Vitest 별칭 해석이 깨져도 CI가 못 잡는다
  (typecheck/build는 잡는다).

**구조·가독성**
- `runCollect`가 약 140줄. 소스별 본문을 헬퍼로 빼면 유지보수가 쉬워진다.
- `listMonths`/`listWeeks`가 ENOENT-catch-and-filter 패턴을 중복한다.
- `arxiv.ts`가 summary에 공백 정규화를 두 번 건다(`collapse()` 후 `toExcerpt()`).
- `formatIssues()`가 `z.ZodError` 대신 손수 만든 구조적 타입을 쓴다.
- `pipeline/registry.ts`의 중복 id 검사가 도달 불가능하다(파일명==id가 이미 강제됨).

**테스트 커버리지**
- `report.merged`가 0이 아닌 값으로 단언되는 곳이 없다.
- arXiv 페이싱(`ARXIV_MIN_INTERVAL_MS`)이 어떤 테스트에서도 실행되지 않는다(arXiv 소스가
  둘 이상인 시나리오가 없다).
- `itemsByField`의 "재정렬하지 않음" 불변식이 검증되지 않는다(픽스처의 두 필터가 각각 항목

- `Monogram`의 initials/hue 결정성, `format.ts` 헬퍼에 테스트가 없다.
- 스토어의 복합 케이스(디스크에 있으면서 같은 호출에 두 번)에 명시적 테스트가 없다.

- `readJson`이 파일 내용이 리터럴 `null`/`0`/`false`인 경우를 파일 없음과 동일하게 취급한다.
- 잘못된 URL 항목은 `seenIds`에 안 들어가서 매 실행마다 재평가된다(저비용, 무해).
- `youtube.test.ts`에 `toEqual` 뒤의 중복 `toHaveLength(2)`가 있다.
- `buildPrompt` 테스트 하나가 앞 테스트의 단언을 그대로 반복한다.

**개선 여지 (결함 아님)**
- LLM이 고른 pick이 걸러졌을 때 휴리스틱 pick으로 자리를 채우면 하이라이트가 3개를 유지한다.

## 7. 환경에서 배운 것 (다시 헤매지 말 것)

- **레포 디렉터리가 0777이면 `next build`가 실패한다.** 이 환경은 world-writable 디렉터리에
  대해 `access(2)` 쓰기 검사를 거부하는데, Next가 빌드 전에 정확히 그 검사를 한다.
  `chmod 775`로 해결했고 umask가 002라 새로 생기는 디렉터리는 문제없다. **NFS 마운트 자체는
  원인이 아니다** — 처음에 그렇게 오진했다가 사용자 지적으로 바로잡았다.
- **`.next`를 공유하는 빌드를 동시에 돌리면 서로 깨진다.** NFS라 `.nfs*` 잠금 파일이 남고
  `rm -rf .next`가 EBUSY로 실패한다. 에이전트를 병렬로 돌릴 때 빌드가 겹치지 않게 할 것.
  증상이 코드 결함처럼 보이므로 주의.
- **구현 에이전트는 한 번에 하나만.** 둘이 동시에 전체 테스트를 돌리면 서로의 미완성 상태를
  본다. 리뷰어(읽기 전용)와 구현자를 병렬로 돌리는 건 안전하다.
- `shellcheck` 없음. `gh` 인증됨. `vercel` CLI 설치됨(로그인 상태 미확인).
- `content/`는 `.gitignore`에 **없는 것이 맞다** — 워크플로가 커밋하는 데이터 저장소다.
  개발 중 생성한 것은 커밋 전에 지울 것.

## 8. 이 프로젝트의 리뷰에서 반복된 교훈

계획서에 넣은 테스트 코드가 **동작을 보여주기만 하고 회귀를 잡지 못하는** 경우가 반복됐다
(Atom summary 폴백, `toExcerpt` 정규식, `asArray` 단일 항목 경로, 드롭 가드, 태그 상한,
`seenIds` 절단 방향). Task 6부터 지시에 **드롭 가드·퇴화 입력 커버리지와 뮤테이션 확인**을
미리 요구했더니 첫 리뷰에서 통과하기 시작했다. 남은 작업에도 같은 방식을 쓸 것:

> 각 테스트가 제 몫을 하는지 증명하라. 대상 로직을 일부러 깨뜨려 해당 테스트가 실패하는지
> 확인하고, 원상 복구한 뒤 `git diff`가 비었는지 확인해 보고하라.
